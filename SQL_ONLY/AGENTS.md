# SQL実装ガイド（SQL Files + Schema + Seed Data）

## 目的
このガイドは、アプリケーションコードではなく SQL そのものを作成・管理する作業に特化した実装方針を定義する。

- SQL は用途単位で `.sql` ファイルに分けて管理する
- スキーマ、初期データ、検証用データの責務を分離する
- SQL で自然に解決できる処理は SQL で表現する
- 可読性、保守性、実行計画を優先して SQL を設計する

## 適用範囲
- 検索 SQL
- 集計 SQL
- スキーマ定義 SQL
- 初期データ投入 SQL
- DB 方言差分の SQL

## 基本方針

### 1. SQL は用途ごとにファイルを分ける
- 1つの SQL ファイルには 1 つの目的だけを持たせる
- 検索 SQL とスキーマ SQL とデータ投入 SQL を混在させない
- クエリをアプリコードへ直書きしない
- ファイル名は役割が分かる名前にする
  - 例: `high_skill_users_search.sql`
  - 例: `department_monthly_totals.sql`
  - 例: `schema.sql`
  - 例: `data.sql`

### 2. SQL で自然に書ける処理は SQL で解決する
- 集計、絞り込み、JOIN、存在判定、並び替えは、まず SQL で表現することを検討する
- SQL で自然に書ける処理を、不要にアプリケーション側へ逃がさない
- 重複排除が不要なら `UNION ALL` を優先する
- 安定した結果比較のために `ORDER BY` を明示する
- 1回のSQLで取得・判定・更新まで表現できる場合は、SQLだけで完結させる

### 3. 1クエリに詰め込みすぎない
- SQL 1本で書けても、可読性・保守性・実行計画が悪化するなら分割してよい
- 以下のような場合は分割を検討する
  - JOIN が増えすぎて意図が読みにくい
  - サブクエリや CTE が過剰にネストする
  - DB 方言差分の吸収が困難になる
  - EXPLAIN で不利な実行計画になる

## スキーマ管理

### 正本の原則
- スキーマ定義の正本は 1 つに決める
- 正本は `schema.sql` とし、DDL を二重管理しない
- DB ごとの差分は `patches/` に閉じ込める

### 実務ルール
- スキーマ変更は必ず正本から更新する
- 差分 SQL は最小限に留める
- 空 DB に対して先頭から投入できる状態を維持する
- テーブル定義、インデックス、制約は SQL 上で明示する
- 原則すべてのテーブルに `created_at` と `update_at` を付与する
- 履歴系テーブルには `update_at` を付与しない
- status は `CHECK` 制約ではなく status マスタテーブルを作成し、外部キー参照で管理する

## 初期データ・テストデータ管理

### データの責務を分ける
- `data.sql`: 開発確認用の最小初期データ
- `master_data.sql`: 固定マスタデータ
- `testdata/*.sql`: テストケース専用の検証データ

### ルール
- テスト用データを `data.sql` に混ぜない
- 画面確認用の大量データを正本データに入れすぎない
- テストは必要な前提データだけを投入する前提で設計する
- データ件数や並び順に暗黙依存しない

## SQL ファイルの書き方

### 冒頭コメントを必須にする
各 SQL ファイルの先頭に、少なくとも以下を記載する。

```sql
-- 目的: skill_level >= 8 の社員をカテゴリ横断で取得する
-- 出力カラム: employee_id, employee_name, skill_category, skill_name, skill_level
-- 実装方針: カテゴリごとの結果を UNION ALL で結合し、employee_id, skill_category, skill_name でソートする
```

### 記述ルール
- `SELECT *` を避け、取得カラムを明示する
- 列名、別名、並び順は意図が分かる形にする
- SQL のインデントと改行ルールを揃える
- 比較・検証が必要な SQL では `ORDER BY` を省略しない
- コメントは「何をしているか」ではなく「なぜそうしているか」を書く

## DB 別運用

### 原則
- MySQL / PostgreSQL で完全に別管理するのではなく、正本は共通化する
- DB 固有差分だけを別ファイルに分離する

### 分けるべきもの
- DDL の型差分
- 採番方式の差分
- upsert 構文差分
- 日付関数や真偽値表現の差分
- DB ごとに最適化が必要な検索 SQL

### 分けなくてよいもの
- そのまま両 DB で動く検索 SQL
- 単純な seed data
- 業務ルール自体の表現

## レビュー観点
- SQL の目的がファイル名と冒頭コメントで伝わるか
- クエリの責務が 1 つに収まっているか
- SQL でやるべき処理をアプリ側へ逃がしていないか
- 逆に、SQL に詰め込みすぎていないか
- `ORDER BY` が明示されているか
- インデックスや結合条件が妥当か
- DB 差分の置き場が適切か

## ベストプラクティス
- SQL は用途別に `schema` `seed` `queries` `testdata` へ分ける
- 正本は 1 つにし、DB 差分だけを分離する
- SQL で自然に解ける処理は SQL に寄せる
- ただし可読性と実行計画が悪化する場合は分割する
- SQL ファイル冒頭に目的・出力カラム・実装方針を残す
- `SELECT *` を避け、`ORDER BY` を明示する
- Go + GORM から呼び出す場合は、生クエリを `Raw` / `Exec` で実行する
