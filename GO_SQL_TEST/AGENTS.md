# Go SQLテスト実装ガイド（SQL Files + MySQL/PostgreSQL + Go Testing）

## 目的
このガイドは、SQL をアプリケーションコードから分離して管理し、Go のテストファーストで安全に育てるための実装方針を定義する。

- SQL は文字列直書きではなく `.sql` ファイルとして管理する
- DB スキーマと初期データは再現可能な形で投入できるようにする
- DB を使う検証は実 DB に対する統合テストで確認する
- SQL と Go の責務を明確に分け、可読性と保守性を優先する

## 適用範囲
- Go から SQL ファイルを読み込んで実行する実装
- MySQL / PostgreSQL の両方を視野に入れた SQL 資産管理
- スキーマ、初期データ、検証用テストデータの運用

## 基本方針

### 1. SQL は別ファイルに切り出す
- クエリ文字列を Go コードやテストコードに直書きしない
- 1ユースケース 1SQL ファイルを基本とする
- 複数用途で共用しない。用途が違うなら SQL ファイルも分ける
- SQL ファイル名は `何を返すか` が分かる名前にする
  - 例: `high_skill_users_search.sql`
  - 例: `department_monthly_totals.sql`

### 2. SQL で自然に書ける処理は SQL で解決する
- 集計、絞り込み、JOIN、存在判定、並び替えは、まず SQL で表現することを検討する
- SQL で自然に書ける処理を、アプリ側のループや後処理に逃がさない
- 重複排除が不要なカテゴリ横断結合は `UNION ALL` を優先する
- テストで安定比較できるよう `ORDER BY` は明示する
- 1回のSQLで取得・判定・更新まで表現できる場合は、アプリ側で分割せずSQLで完結させる

### 3. 無理に 1 クエリへ詰め込まない
- 1クエリで実現できても、可読性・保守性・実行計画が悪化するなら分割してよい
- SQL を分割する判断は以下を基準にする
  - JOIN が増えすぎて意図が読みにくい
  - サブクエリや CTE が過剰にネストする
  - DB 方言差分の吸収が困難になる
  - EXPLAIN で明らかに不利な実行計画になる
- アプリケーション側の後処理は、SQL で書く方が不自然な場合に限定する

## DB投入と実行環境

### 方針
- `scripts/bootstrap-db.ps1` を DB セットアップの起点とする
- `postgres` / `mysql` の両エンジンで投入できる状態を維持する
- 元データソースは `sql/spring_boot_resources/schema.sql` と `data.sql` を正とする
- MySQL 向け調整は投入時または方言差分用ファイルで吸収し、元 SQL の改変は最小限に留める

### 実務上のルール
- `schema.sql` は DDL の正本として扱う
- `data.sql` は開発用の最小初期データとして扱う
- テスト専用データは `data.sql` に混ぜず、テストケースごとに追加投入する
- 開発初期データとテスト検証データは目的が異なるため分離する
- 原則すべてのテーブルに `created_at` と `update_at` を付与する
- 履歴系テーブルには `update_at` を付与しない
- status は `CHECK` 制約ではなく status マスタテーブルを作成し、外部キー参照で管理する

## スキーマ管理のベストプラクティス

### 正本の考え方
- 正本は 1 つに決める
- 今回は `sql/spring_boot_resources/schema.sql` をスキーマ正本とする
- テーブル定義を Go の migration と SQL ファイルで二重管理しない

### 運用ルール
- スキーマ変更時は `schema.sql` を先に更新する
- DB 方言差分は `sql/dialect/{engine}` に閉じ込める
- 変更後は bootstrap で空 DB を再構築し、最初から投入できることを確認する
- 投入順に依存するなら、スクリプト側で順序を固定する

## 初期データ・テストデータ管理のベストプラクティス

### 役割を分ける
- `data.sql`: 開発者が画面確認やローカル動作確認に使う最小データ
- テストケース投入データ: 各テストで必要な分だけ投入する検証用データ
- 共通マスタデータ: 頻繁に必要なら別ファイル化して bootstrap 時に投入する

### 推奨ルール
- テストに不要な大量データを `data.sql` に入れない
- テストが特定データ順や既存件数に依存しないようにする
- 各テストは自分で前提データを作る
- クリーンアップはトランザクションロールバック、またはテーブル再初期化で確実に行う

### 望ましい投入単位
- スキーマ投入: `schema.sql`
- 開発用初期データ投入: `data.sql`
- 方言差分投入: `sql/dialect/{engine}/patches.sql`
- テストケース固有データ投入: Go テスト内、または `testdata/*.sql`

## SQL ファイルの書き方

### 冒頭コメントを必須にする
各 SQL ファイルの先頭に、少なくとも以下を書く。

```sql
-- 目的: skill_level >= 8 の社員をカテゴリ横断で取得する
-- 出力カラム: employee_id, employee_name, skill_category, skill_name, skill_level
-- 実装方針: カテゴリごとに抽出した結果を UNION ALL で結合し、比較しやすいよう employee_id, skill_category, skill_name でソートする
```

### 書き方のルール
- `SELECT *` は避け、取得カラムを明示する
- テストで比較する列の並び順を固定する
- 別名は省略しすぎず、意味が通る名前にする
- SQL ファイルはフォーマットを揃える
- プレースホルダの方式は呼び出し側ライブラリと整合させる

## Go 側の実装方針

### SQL ローダー
- SQL ファイル読み込み処理を共通化する
- アプリコードはファイルパスを知っていても、SQL 文字列の中身は持たない
- キャッシュを入れる場合も、まずは単純なローダーで開始してよい

### リポジトリ / クエリ実装
- SQL 実行は `internal/infrastructure/query` などの境界に寄せる
- 複雑な検索系は GORM のチェインより `Raw` を優先してよい
- 更新系でも複雑なバルク処理や集計更新は SQL ファイル化を検討する
- Go + GORM 構成では、生クエリを `Raw` / `Exec` で実行し、アプリ側での多段分岐を減らす

## テストファースト（Go）

### ルール
- SQL を追加するときは、先に Go の `_test.go` を作る
- 失敗を確認してから SQL ファイルを追加する
- DB を使う検証は実 DB への統合テストで行う
- テスト関数名は英語、`t.Run` の表示名は日本語で書く
- テスト内にクエリ文字列を書かず、`sql/*.sql` を読み込んで実行する

### テスト観点
- 正常系: 期待した行が返る
- 並び順: `ORDER BY` 通りに返る
- 境界値: しきい値ちょうどの値を含むか
- 空結果: 該当データがないときに 0 件になるか
- 方言差分: MySQL と PostgreSQL の差が結果に影響しないか

## 今回の代表実装
- 対象 SQL: `sql/high_skill_users_search.sql`
- 対象テスト: `test/integration/high_skill_users_mysql_test.go`
- 目的: `skill_level >= 8` の社員をカテゴリ横断で抽出し、スキル名・レベルを返す

## 作業手順
1. 先に統合テストを追加し、期待結果を定義する
2. 必要なテストデータを投入する
3. `sql/queries/*.sql` に SQL を追加する
4. Go から SQL ファイルを読み込んで実行する
5. `go test` で成功を確認する
6. 実行計画と可読性を見て SQL を必要に応じて分割する

## ベストプラクティス
- SQL の正本、開発用初期データ、テストデータを分離する
- SQL で自然に表現できる処理は SQL に寄せる
- ただし 1 クエリに詰め込みすぎず、可読性と実行計画を優先する
- 方言差分はアプリコードではなく SQL 資産または bootstrap で吸収する
- SQL ファイルは用途単位で分け、冒頭コメントで意図を残す
- テストは SQL ファイルを読み込んで実行し、直書きしない
- DB を使う検証は実 DB で行い、プロセス内モックに逃げない
