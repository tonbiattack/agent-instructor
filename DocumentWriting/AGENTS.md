## 設計文書作成ルール

### 基本方針

- 設計文書の作成では、正確性・読みやすさ・保守しやすさを優先する。
- 出力はプレーンテキストとする。Google ドキュメントおよび Google スプレッドシートへの転記を前提とする。
- Markdown の装飾（`**...**` による強調、`---` による区切り線）は使用しない。
- AI 的な繰り返し強調表現や記号装飾は避ける。
- 人が書いたように読める、自然な日本語の文語体で記述する。
- 文章は簡潔・明瞭に保つ。見出し・短い段落・箇条書きを適切に使い分ける。

### 文体ルール

- 文末は「〜である。」「〜とする。」「〜を行う。」など文語調に統一する。
- 「〜です。」「〜ます。」などの口語調は使用しない。
- 主語を省略しない。主体が誰か・何かを明示する。
- 曖昧な表現（「など」「場合によっては」「〜かもしれない」）は極力排除する。
- 体言止めは箇条書き項目に限定し、文中では使用しない。

### 文書種別と構成

以下の文書種別に対応する。種別に応じた構成を用いること。

#### 要件定義書

1. 目的
2. 背景・課題
3. スコープ（対象範囲・対象外）
4. 機能要件
5. 非機能要件
6. 制約事項
7. 用語定義

#### 基本設計書

1. システム概要
2. アーキテクチャ概要
3. 機能一覧
4. 画面一覧（該当する場合）
5. データ設計概要
6. 外部インタフェース
7. 非機能設計方針

#### 詳細設計書

1. 対象機能の概要
2. 処理フロー
3. クラス・モジュール設計
4. データアクセス設計
5. エラー処理方針
6. 例外・境界値の扱い

#### その他の文書

上記に該当しない場合は、以下の構成を基本とする。

1. 目的
2. 背景・前提
3. 内容
4. 制約・注意事項

### 入力の受け取り方

文書作成時には以下を入力として受け取る。

- サンプル文書（任意）: 文体・フォーマットの参考として使用する。提供された場合は、その文書の構成・言葉遣いに合わせる。
- 作成対象の文書種別: 上記の文書種別から指定する。
- 素材情報: 要件メモ・他者が記載した情報・箇条書きのメモなど、文書化したい内容の素材。

### サンプル文書が提供された場合の処理

1. サンプル文書から以下を読み取る。
   - 見出しの階層と命名規則
   - 文末表現のパターン
   - 項目の粒度と順序
   - 会社固有の用語・表記
2. 読み取った規則を本文書のルールより優先して適用する。
3. サンプルに存在しない項目については本ルールに従う。

### 出力ルール

- 出力はプレーンテキストのみとする。
- Markdown の記法（見出し記号 `#`、コードブロック ` ``` `、太字 `**`）は使用しない。
- 見出しは「1. 」「1.1. 」などの番号付きで表現する。
- 箇条書きは「・」を使用する。
- 図が必要な場合は、図の内容をテキストで説明する形式で代替する。
- 文書全体を一度に出力する。途中で確認を求めない。

### やらないこと

- 素材に記載のない内容の推測・補完（不明点は文書内に「〔要確認〕」と明示する）
- 技術スタックや言語・フレームワークへの依存した記述
- フォーマット変更（指定された種別の構成を勝手に変えない）
- サンプル文書が提供されていない場合に、サンプルがあると仮定した処理
