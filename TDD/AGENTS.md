# TDD（テスト駆動開発）ガイド

## テスト手法の方針（古典派）
このプロジェクトのテスト方針は、いわゆる「古典派（Classicist）」です。

- **実DB（テスト用DB）を使用**: DBアクセスを伴うテストは実DB（テスト用DB）を使用
- **プロセス内処理はモック不要**: DBレイヤーやリポジトリなど、プロセス内で完結する処理にモックを使用しない
- **プロセス外のみモック**: 外部API・他システム連携・メール送信・キュー等、プロセス外との結合のみモック/スタブを利用
- **内部実装のモック禁止**: DBモックやリポジトリモックをテストコードの外側に公開しない
- **状態検証中心**: ロンドン派（Mockist）ではなく、状態検証中心のテストを優先

## 基本サイクル: Red-Green-Refactor

### Red - 失敗するテストを書く
1. 小さな機能単位でテストを作成
2. テストを実行して失敗を確認（実装がないため）
3. 何を実装すべきか明確にする

### Green - テストを通す最小実装
1. テストが通る最小限のコードを書く
2. すべてのテストが成功することを確認
3. 美しさより動作を優先（まず動かす）

### Refactor - コードを改善
1. 重複を排除し、構造を改善
2. デザインパターンを適用
3. テストを再実行して成功を確認
4. テストコード自体もリファクタリング対象

## 作業ルール
- Red-Green-Refactorを厳密に守る
- 一度に一つの機能に集中（小さなステップ）
- **テスト名（test name）は日本語で記載**
  - 理由: Test Explorer 上で一覧した際に、仕様単位でのテストケース漏れを視認しやすくするため
  - 例: `Test金額計算_手数料込み`、`Test集計条件_週間合計10万円超`
- テストは常にグリーン（成功）を維持
- リファクタリングはテスト成功時のみ
- **DBアクセスは実DB（テスト用DB）を使用**
- **プロセス内処理（DBレイヤー、リポジトリ）にモックを使用しない**
- **プロセス外結合（外部API、メール送信等）のみモック/スタブを利用**
- **1回のSQLで効率よく取得・判定できる処理はSQLで完結させる**
- **Go + GORM を使う場合は生クエリを `Raw` / `Exec` で実行する**
- 各サイクル完了時にコミット

## サイクル例
```
1. Red:     getUserById のテスト作成 → 失敗確認
2. Green:   getUserById の最小実装 → テスト成功
3. Refactor: エラーハンドリング追加 → テスト成功

4. Red:     バリデーションのテスト追加 → 失敗確認
5. Green:   バリデーション実装 → すべて成功
6. Refactor: 共通処理を抽出 → すべて成功
```

## ディレクトリ構成例
```
プロジェクト/
├── src/
│   └── user.ts              # 実装コード
└── tests/
    ├── unit/
    │   ├── user.test.ts
    │   └── user.validation.test.ts
    ├── integration/
    │   └── user.integration.test.ts
    └── e2e/
        └── user.e2e.test.ts
```

## TDDのメリット
- バグの早期発見
- テストしやすい設計
- リファクタリングの安全性
- テストが仕様書になる
- 開発速度の向上

## チェックリスト
- [ ] Red: 失敗するテストを書いた
- [ ] Red: テスト実行して失敗を確認した
- [ ] Green: 最小限の実装を書いた
- [ ] Green: すべてのテストが成功した
- [ ] Refactor: コードを改善した
- [ ] Refactor: テスト再実行して成功を確認した
- [ ] コミットした
