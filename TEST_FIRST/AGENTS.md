# テストファースト開発ガイド

## 基本原則
実装コードを書く前に、必ずテストコードを先に作成する。

## テスト手法の方針（古典派）
このプロジェクトのテスト方針は、いわゆる「古典派（Classicist）」です。

- **実DB（テスト用DB）を使用**: DBアクセスを伴うテストは実DB（テスト用DB）を使用
- **プロセス内処理はモック不要**: DBレイヤーやリポジトリなど、プロセス内で完結する処理にモックを使用しない
- **プロセス外のみモック**: 外部API・他システム連携・メール送信・キュー等、プロセス外との結合のみモック/スタブを利用
- **内部実装のモック禁止**: DBモックやリポジトリモックをテストコードの外側に公開しない
- **状態検証中心**: ロンドン派（Mockist）ではなく、状態検証中心のテストを優先

## 作業手順

### 1. 要件を理解する
- ユーザーストーリーや仕様を確認
- 期待される動作を明確にする

### 2. テストケースを設計する
- 正常系、異常系、境界値をリストアップ
- テストすべき項目を洗い出す

### 3. テストコードを作成する
- 実装前に失敗するテストを書く
- テストケース名で何をテストするか明示する
- 各テストは独立して実行可能にする

### 4. インターフェースを定義する
- テストから必要な関数・クラスのシグネチャを決める
- 実装すべきAPIを明確にする

## ルール
- テストは実装前に必ず作成
- **テスト名（test name）は日本語で記載**
  - 理由: Test Explorer 上で一覧した際に、仕様単位でのテストケース漏れを視認しやすくするため
  - 例: `Test金額計算_手数料込み`、`Test集計条件_週間合計10万円超`
- テストコードは読みやすく保守しやすい構造
- **DBアクセスは実DB（テスト用DB）を使用**
- **プロセス内処理（DBレイヤー、リポジトリ）にモックを使用しない**
- **プロセス外結合（外部API、メール送信等）のみモック/スタブを利用**
- **監査カラムは原則必須**: 全テーブルに `created_at` と `update_at` を付与する
- **履歴系テーブルは例外**: 履歴系テーブルには `update_at` を付与しない
- **status はマスタ管理**: `CHECK` 制約ではなく status マスタテーブルを作成し、外部キーで参照する
- **1回のSQLで効率よく取得・判定できる処理はSQLで完結させる**
- **Go + GORM を使う場合は生クエリを `Raw` / `Exec` で実行する**
- 一つの実装に複数のテストファイルがあってもOK
  - 単体テスト: `user.test.ts`
  - 統合テスト: `user.integration.test.ts`
  - E2Eテスト: `user.e2e.test.ts`
